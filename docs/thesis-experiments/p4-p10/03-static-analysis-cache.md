# 03. 정적 분석 성능과 SourceFile 캐시 개선

## 1. 측정 방법 (Node, 확장과 같은 분석 코드)
- 확장의 컴파일 산출물 `out/analyzer`를 Node에서 직접 호출했다. 패널의 결과 캐시 규칙(키, JSON 복제, LRU 40)을 재현했다.
- 측정 구간: 결과 캐시 조회 + `analyzeWorkspaceActive()` + Depth 0 가지치기 + payload 직렬화.
- 시나리오: Cold Start(표본마다 새 프로세스), Warm(반복마다 캐시 비움), 동일 그래프 반복, 활성 파일 편집(매 반복 함수 한 개 추가).
- 블록마다 새 프로세스, 블록 순서 교차, warm-up 3 + 측정 15 × 2블록(Cold Start는 모드당 10 프로세스, P9 변형 비교는 2).
- 대상: 결정적 합성 워크스페이스(`entry → service → helper → utility`) 100·500·1,000·2,000파일, 4파일 fixture, Cogic 저장소.

## 2. 문제 (P6, 기존 캐시, `9126f35` 분석기)
활성 파일 편집, 확장 측 처리 시간 중앙값(ms), 캐시 OFF → ON:

| 파일 | OFF → ON | 감소율 [bootstrap 95% CI] |
|---:|---|---|
| 100 | 389.3 → 35.7 | 90.8% [90.2, 91.6] |
| 500 | 686.1 → 74.7 | 89.1% [88.5, 89.4] |
| 1,000 | 1,024.6 → 1,133.9 | **−10.7% (ON이 느림)** [−13.2, −9.3] |
| 2,000 | 1,816.7 → 2,026.8 | **−11.6% (ON이 느림)** [−13.0, −10.7] |

동일 그래프 반복 분석은 결과 캐시 적중으로 모든 규모에서 0.1–3.9 ms였다. Cold Start·Warm에서는 캐시 이득이 없었다. 원자료: [data/p6/](data/p6/).

## 3. 원인 (P9)
- 구현: 고정 800개 LRU. 용량을 넘으면 삽입할 때마다 전체 항목을 정렬한다.
- 분석 1회에 접근하는 SourceFile(루트 + TypeScript lib): 100파일 150, 500파일 550, **1,000파일 1,050, 2,000파일 2,050**.
- 같은 순서로 반복 접근하는 작업 집합이 용량보다 크면, LRU는 다음에 필요한 항목을 먼저 내보낸다(순환 스캔 스래싱). 측정 결과 적중 0, 미적중 1,050/2,050이었다.

## 4. 정책 비교 (P9, Node, 활성 파일 편집, 중앙값 ms, n=30)

| 파일 | 기존(800 LRU) | O(1) LRU | scan-resistant | **adaptive** | 적중률(기존 → adaptive) | 유지 캐시 힙(기존 → adaptive) |
|---:|---:|---:|---:|---:|---|---|
| 1,000 | 1,258.0 | 1,304.1 | 558.0 | **139.4** | 0% → 100% | 66.7 → 72.4 MB |
| 2,000 | 2,218.1 | 2,035.6 | 1,428.3 | **253.5** | 0% → 100% | 72.0 → 103.6 MB |

정렬 비용을 O(1)로 바꾸는 것만으로는 개선되지 않았다(lru). 100·500파일은 모든 정책이 같았다. 원자료: [data/p9/p9-cache-variants.csv](data/p9/p9-cache-variants.csv).

## 5. 채택 정책 (`e753f5e`)
- 분석마다 용량 = max(800, ⌈1.1 × 루트 파일 수⌉ + 200), 상한 4,400
- 캐시된 소스 텍스트 합계 2,400만 문자 상한. 상한을 넘으면 현재 분석에서 사용한 항목은 내보내지 않고 새 파일을 캐시하지 않는다(scan-resistant 대체).
- 최근성 순서를 Map 삽입 순서로 유지(O(1))
- 단위 테스트 3개: 900파일 작업 집합에서 두 번째 편집 분석 miss 0 / 캐시 ON 그래프 = OFF 그래프 / 디스크에서 바뀐 파일은 stale로 다시 읽음
