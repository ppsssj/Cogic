# 04. 실제 VS Code에서 그래프 생성·갱신 응답 시간

## 1. 측정 방법
- 격리 VS Code 1.147.0(별도 사용자 데이터·확장 폴더), 창 1600×960, Playwright로 실제 클릭·키 입력.
- 웹뷰 안의 수동 관찰 코드(이벤트 주입 없음): 입력 이벤트 `timeStamp`, `analysisResult` 메시지 수신, React Flow 노드·엣지 DOM의 마지막 변경(MutationObserver), 그 뒤 두 번째 `requestAnimationFrame` 콜백. 시각은 `performance.timeOrigin + performance.now()`.
- 측정 값 = **입력 → 프레임 콜백**. 편집 후 갱신은 마지막 키 입력부터이며 350 ms debounce를 포함한다.
- 실행 1회 = VS Code 새 프로세스 1회(첫 Generate 1 + 반복 Generate 5 + 편집 5). 조건당 3회, 버전 순서 교차(B,V,V,B,B,V / V,B,B,V,V,B).
- 편집 표본은 새 함수 노드가 그래프 DOM에 있고, 뷰포트 안에 있으며, hit-test를 통과할 때만 유효하다. 1,000파일 이상에서는 측정 구간 밖에서 실제 마우스 드래그로 활성 파일 그룹을 화면 안으로 옮긴 뒤 판정했다([06](06-graph-interaction.md) 1절 참고).
- 판정: 실행별 중앙값 3개가 모두 반대편 3개보다 작을 때만 개선/악화(사전 규칙). 그 외에는 "차이 불분명". 통계적 유의성 검정이 아니다.

## 3. Baseline 빌드의 규모별 응답 (P6·P8, `9126f35`, 캐시 OFF → ON)
입력 → 프레임 콜백, 실행 3회 중앙값(ms). 4–500파일은 P6(Fit 상태에서 화면 반영 확인), 1,000–2,000파일은 P8(활성 그룹을 화면에 둔 상태).

| 파일 | 그래프(노드/엣지) | 반복 Generate OFF → ON | 편집 후 갱신 OFF → ON |
|---:|---|---|---|
| 4 | 7/7 | 681.6 → 198.6 | 685.5 → 498.0 |
| 100 | 12/19 | 691.0 → 141.6 | 972.1 → 515.3 |
| 500 | 48/91 | 906.6 → 166.6 | 1,248.3 → 573.5 |
| 1,000 | 92/179 | 1,974.3 → 232.4 | 1,192.0 → **1,385.7(ON이 느림)** |

1,000파일 이상에서 기존 캐시를 켜면 편집 갱신이 느려지는 현상을 실제 UI에서 확인했다. 이것이 [03](03-static-analysis-cache.md)의 개선 동기다. 원자료: [data/p6/p6-ui-r3-per-run.csv](data/p6/p6-ui-r3-per-run.csv), [data/p8/p8c-per-run.csv](data/p8/p8c-per-run.csv).

## 4. 응답 시간 구성
- 대부분은 확장 측 분석 구간(입력 → 결과 수신)이다. 결과 수신 후 DOM 반영과 프레임 콜백까지는 4–500파일에서 약 20–55 ms, 2,000파일에서 약 100–130 ms였다.
- VS Code 실행 직후 첫 Generate는 OS 파일 캐시·TS 서버 상태에 따라 1–17초까지 변했고, 측정 순서 효과가 커서 캐시 비교에는 쓰지 않았다(P6 예비 측정의 역순 점검).
