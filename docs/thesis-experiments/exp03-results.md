## 11. 적용 범위와 한계

- **합성 workspace**: 파일이 작고 균일하다. 분석마다 요청 순서가 완전히 같은 순환 접근이다. 실제 편집에서는 여러 파일이 바뀌고 무효화되므로 접근 패턴이 순환이 아닐 수 있다. 그런 경우 LRU의 동작은 여기서 측정하지 않았다.
- **graphDepth 1**: 분석당 Program이 1개다. production에서 depth ≥ 2이면 분석당 Program이 여러 개라 W가 더 커질 수 있다(측정하지 않음).
- **L의 환경 의존성**: L은 cwd의 `node_modules/@types`에 따라 달라진다. 확장 프로그램 호스트의 cwd에서 실제 W가 얼마인지는 측정하지 않았다.
- **메모리 지표**: 강제 GC 뒤의 heapUsed와 RSS다. 50 ms 대기가 필요했던 이유는 확인하지 않았다(protocol-notes §4).
- **H3-5 분해**: microbench는 analyzer 밖에서 재구현해 쟀다. 저하의 44–91%가 설명되지 않은 잔차다.
- **반사실이 없는 조건**: N = 2000 · N = 1442는 측정 용량 중 C ≥ W가 없어 스래싱 기준 5를 검증하지 못했다.
- **단일 장비**: 이 장비의 결과다. 절대 ms는 다른 장비와 비교하지 않는다.

## 12. 논문 5.4절 서술 초안

> **5.4 캐시 용량과 확장성**
>
> SourceFile 캐시 용량(C)이 적중률·분석 시간·메모리에 미치는 영향을 측정하기 위해, analyzer(`bbe4cbf`)의 컴파일 산출물을 복사하고 용량 상수 한 줄만 400, 800, 1,600으로 바꾼 실험 빌드를 사용하였다. 원본 소스와 캐시 로직은 바꾸지 않았다. 주입이 적용되었는지는 점유량으로 확인하였다. 작업 집합 W가 C보다 큰 모든 조건에서 캐시 점유량은 정확히 C였고, C = 800 빌드는 원본 빌드와 모든 count와 결과가 같았다. 분석 1회의 SourceFile 요청 수는 W = N + 159였다. 159개는 TypeScript 표준 라이브러리 선언 51개, 자동 포함된 `@types` 선언 72개, 그 의존 선언 37개에서 active file 1개를 뺀 수다.
>
> 표 5-9와 같이 적중률은 W ≤ C이면 100%, W > C이면 0%였고 부분 적중은 없었다. 경계 실험에서도 세 용량 모두 W = C − 1과 W = C에서 100%, W = C + 1에서 0%였다. 반복 분석은 매번 같은 순서로 요청하였고, 첫 분석 이후 모든 요청의 재사용 거리는 W − 1이었다. 따라서 W > C이면 LRU는 항목을 다시 쓰기 전에 축출한다. 분석마다 축출 수는 miss 수와 같았고 점유량은 C로 포화되었다. 자동 포함 타입 선언을 제외해(`"types": []`) W를 109만큼 줄이자, 같은 파일 수(N = 642)에서 적중률이 0%에서 100%로 바뀌었다. 적중 붕괴는 파일 수가 아니라 작업 집합과 용량의 관계로 결정된다. 기존 측정에서 관찰된 Synthetic-1000·2000의 적중 붕괴는 작업 집합이 용량을 넘을 때 생기는 LRU 스래싱으로 설명된다. 다섯 가지 사전 기준을 모두 충족한 조건은 7개였다. N = 2000은 측정한 용량 중 W를 넘는 것이 없어 반사실 기준을 확인하지 못했다.
>
> 표 5-10에서 용량을 1,600으로 늘리면 Synthetic-1000의 분석 시간은 995.4 ms(OFF)에서 205.4 ms로 79.4%(95% CI 78.4–79.8%) 줄었다. C = 800에서는 OFF보다 10.8% 느렸으므로 성능이 회복된 것이다. 반면 Synthetic-2000(W = 2,159)은 세 용량 모두에서 적중률이 0%였다. 캐시를 켜면 OFF보다 7.8%(C = 400), 14.7%(C = 800), 25.3%(C = 1,600) 느렸다. 즉 W > C인 조건에서는 용량이 클수록 오히려 느려졌다. 저장마다 전체 항목을 정렬하는 축출 방식의 비용은 microbenchmark에서 C에 따라 커졌다(1회 21.7 → 46.1 → 85.9 µs). 파일 상태 확인·캐시 키·정렬 비용과 GC 차이를 더한 분해 추정은 관측된 저하의 9–56%만 설명했고, 나머지는 측정으로 원인을 밝히지 못했다.
>
> 메모리 측면에서(표 5-11) 캐시 보유량은 항목 수보다 항목 종류에 좌우되었다. 선언 파일 160개가 약 91.7 MiB를 차지했고, 합성 workspace 파일은 항목당 약 26.9 KB였다. 그래서 C를 800에서 1,600으로 늘릴 때 늘어난 메모리는 Synthetic-1000에서 10.5 MiB, Synthetic-2000에서 20.7 MiB로 작았다. 따라서 용량 확장의 효과는 W ≤ C가 되는지에 달려 있다. W를 덮는 용량에서는 적은 메모리로 큰 시간 이득을 얻었다. 덮지 못하는 용량을 키우면 이득 없이 메모리와 정렬 비용만 늘었다. 이 결과는 순환 접근을 하는 합성 workspace, graphDepth 1, 단일 장비에서 측정한 것이다. 실제 편집 패턴과 다중 Program 분석으로 일반화하는 것은 후속 과제다.
