# Corpus B 분석 환경 대안 비교 (P1-K2)

- 비교 대상
  - Option A: 현행 untyped shim
  - Option B: 최소 typed shim
  - Option C: 고정 upstream 의존성 설치
- 이번 단계에서는 B와 C를 평가 환경에 적용하지 않았다.
  - C는 TypeScript만 쓰는 읽기 전용 해석 비교로 탐색했다([README.md](README.md) §1.4, [gt-impact-report.md](gt-impact-report.md)).
  - B는 실험하지 않았다. 연구자가 타입을 정의해야 하므로, 정의 자체가 이번 감사의 범위를 넘는다.

## 1. 대안 요약

| | Option A — untyped shim(현행) | Option B — 최소 typed shim | Option C — 고정 의존성 설치 |
|---|---|---|---|
| 구성 | 외부 모듈마다 `declare module "x";`, 파생 tsconfig | 평가에 필요한 외부 API만 연구자가 타입 선언 | upstream lockfile 그대로 설치(`--ignore-scripts`), upstream tsconfig |
| 측정한 사실 | 진단 1,421건(고유 978). 로컬 선언 해석은 C와 같다(차이 0) | 실험하지 않음 | active file 진단 0. 패키지 선언으로 해석되는 지점 198개 |
| Corpus B 고정 상태 | 그대로(v1) | 새 버전이 필요하다(shim·GT 범위 변경) | 새 버전이 필요하다(입력 구성·GT 범위 변경) |

## 2. 기준별 평가

| 기준 | A | B | C |
|---|---|---|---|
| 정적 의미 해석 정확성 | 로컬·lib 선언은 C와 같다. 외부 API는 `any`다. 예외 2건: bn03 `Array.includes`, br01 `useCallback` 반환 함수 | 선언한 API만 정확하다. 선언 품질에 따라 해석이 C와 달라질 수 있다 | 기준(upstream 의도) |
| GT 타당성 | 현행 GT 196개 중 C 기준으로 틀린 관계 0. 정해진 범위(로컬 관계) 안에서 타당하다 | 범위를 넓히려면 외부 API 관계의 정답을 새로 써야 한다. 선언한 타입이 정답을 정하게 된다 | 외부 패키지 선언을 노드로 둘지 정해야 한다. 정하면 관계가 크게 늘어난다(지점 198개) |
| 재현 가능성 | 높다. 저장소 안 파일만으로 재현된다(MANIFEST 601개) | 높다(shim을 저장소에 둔다) | 중간. 레지스트리·패키지 매니저 3종(npm, pnpm 10.33.0, yarn 1.22.22)이 필요하다. 설치 크기가 크고(NestJS 1,248 패키지) 네트워크 실패가 있었다(React 1회 재시도). 저장소 밖에서만 재현된다 |
| 연구자 편향 위험 | 낮다. 연구자가 타입을 정하지 않는다. 대신 범위 결정(A2)이 연구자 몫이다 | **높다.** 어떤 API를 어떤 타입으로 선언할지 연구자가 정한다. 그 선택이 analyzer 결과와 GT 양쪽에 영향을 준다 | 낮다. upstream이 정한 타입을 그대로 쓴다 |
| 환경 구성 비용 | 이미 구성되어 있다 | 중간. API 목록과 선언, 검토가 필요하다 | 높다. 4개 프로젝트 설치, 설치 폴더 관리, 경로 길이 문제(Windows) |
| framework 지원 범위 | framework API 관계는 평가하지 않는다. owner·updates는 구문으로 평가한다 | 선언한 API만 평가할 수 있다 | 전부 평가할 수 있다. 단, GT 확장이 필요하다 |
| Original/Improved 공정 비교 | 두 analyzer가 같은 입력을 받는다. 타입에 의존하는 개선은 이 환경에서 드러나지 않을 수 있다. 다만 해당 관계(React 상태)가 표본에 없다 | 선언한 타입에 따라 한 버전에 유리할 수 있다 | 두 analyzer가 같은 입력을 받는다. 타입 기반 개선이 드러난다. 외부 노드 키가 많아져 채점 충돌 위험이 커진다(P1-F 선례) |

## 3. 측정 근거 요약

- **A의 로컬 해석:** 616개 식별자 중 로컬 대상이 C와 다른 지점과 C에서만 로컬 §2 노드가 되는 지점은 0이다. GT 대상 167개는 C에서 같은 선언으로 확인되었다(gt-impact-report.md §2).
- **A의 범위 밖:** C에서 외부 패키지 선언으로 해석되는 지점은 198개다(Express 56, NestJS 77, React 42, Vue 23). A에서 GT가 정의하지 않은 범위다(A2).
- **A의 예외:** C에서만 대상이 정해지는 호출이 2건(4개 지점) 있다.
  - bn03: lib 호출. unsupported-by-design 관계 2개에 해당한다.
  - br01: `useCallback` 반환 함수. 지침에 규칙이 없다.
- **lib override:** 파생 tsconfig의 DOM 없는 lib을 upstream 기본값으로 바꾸면, Express에서 untyped `Request`·`Response`가 DOM 타입으로 잘못 해석된다(README §2.6). A의 override가 맞다.
- **C의 실현 가능성:** 4개 프로젝트 모두 설치되었고, active file 진단은 0이다. lockfile은 바뀌지 않았다.

## 4. 결론

- A는 연구 질문을 "코퍼스 안에 선언된 함수·클래스·타입 사이의 관계 정확도"로 제한할 때 타당하다. 그 범위 안에서 C와 해석이 같다.
- B는 연구자 편향 위험이 가장 크다. 그러면서 A의 범위 문제를 일부만 줄인다. 권하지 않는다.
- C는 framework API와 외부 타입 관계까지 평가하려 할 때만 필요하다. 그 경우 다음 일이 따른다.
  - GT 범위를 새로 정하고 외부 패키지 노드를 정의하는 새 Corpus B 버전을 만든다.
  - 사람 검토를 다시 한다.
  - 이것은 현재 연구 질문을 넘어서는 확장이다.
